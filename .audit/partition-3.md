## 결함 (심각도 순)

### [D3] docs/domain-design.md:902 (§10.2 재검증 검사 목록) — 치명

문제 — 재검증 검사 목록에 **한도 축(`maxStopCnt`·`maxDriveTime`·`maxDriveDist`, §2.6)이 없다.** servicePattern(DELIVERY_ONLY 가짜 픽업 금지)·경로 종료 load=0·경로 중간 차고 재방문 금지·차량-경로 유일성도 목록에 없다.
근거 — 902행 검사 행 전체 인용: "pair·XOR(§6.3), 선행, 적재 곡선, 시간창·`reqDate`·근무창(다일)·차고 창, 이동표 사용, profile hard" — 한도 없음. 반면 §6.2(554행)는 hard에 "maxStop·maxDrive"를 명시하고, §2.6(347~350행)은 "**탐색과 재검증이** 이 경계를 다르게 읽으면 안 되는 실전 근거: Win 참조 해가 정차 28회 = 한도 28 경계 위에 실재한다 (2026-08-11 실측)"라고 재검증의 한도 판정을 명시 전제한다. fixture: `options['Optimizer.VehicleMaxStopCount']='28'` 실재. 한도는 canonical Vehicle 필드(223행)라 profile hard로도 포섭되지 않는다.
증상 — Stage 5가 §10.2 표만 보고 구현하면(이 표가 재검증의 유일한 검사 명세다) 탐색 코드의 maxStop 버그로 정차 29회 해가 나와도 재검증 PASS → **한도 위반 배차안이 result.json으로 발행**된다. §2.6이 경계 대조를 요구한 바로 그 축이 안전망에서 빠진다.
권고 — 문구 분리: §10.2 검사 행에 "§6.2 표 전 항목 + §2.6 한도 축(경계 포함)"을 전수 나열로 개정.

### [D3] docs/domain-design.md:682-693 (§7.2 숫자 예) — 중

문제 — 전파 숫자 예의 경로(차고A → R2픽 → R1배)가 문서 자신의 MUST 두 개를 어긴다: R2 pair 미완(R2배 방문 없음 — §6.3 XOR)이고 경로 종료 load=10≠0(§6.2 "경로 종료 시 load = 0 // 미완료 pair로 우회 금지").
근거 — 537행이 R2 = PICKUP_DELIVERY로 정의하고 §6.1의 대응 예(537행)는 "차고A → R2픽 → R1배 → R2배"로 R2배가 있는데, §7.2(682~684행) 경로와 표(687~693행)는 R1배 "배송 후 **10**"에서 끝난다. 재검산: initialLoad 10(R1) → R2픽 +10 = 20 → R1배 −10 = **10에서 종료**.
증상 — 이 예를 그대로 전파 단위 테스트로 옮기면 구조 검사(pair·종료 load=0)가 있는 구현에서 불가 판정이 나와 기대값과 충돌한다. 구현자가 "전파는 pair 미완 경로도 허용하는가"를 되묻게 된다.
권고 — 문구 교정: 경로에 R2배 방문을 추가하고 표에 한 행 보충해 §6.1 예와 일치시킨다.

### [D1] docs/domain-design.md:757-758 (§7.4 stopCount) — 중

문제 — "직전 고객 서비스 장소와 이번 장소가 다르면 +1"은 **직전 고객이 없는 첫 방문**의 +1 여부를 정의하지 않는다.
근거 — 757~758행 인용. 오독 시나리오: Stage 3(탐색)은 괄호의 "첫 진입만 +1"을 근거로 첫 방문 +1, Stage 5(재검증)는 본문을 문자 그대로 읽어 "직전이 없으면 비교 불가 → +0" — 서로 다른 장소 n곳 경로에서 n vs n−1.
증상 — ① §10.2가 metric 재계산 대조를 요구하고 §7.3이 stopCount를 기록값에 넣으므로, 1 차이만으로 **정상 해가 재검증 FAIL → 결과 미저장.** ② maxStopCnt 판정이 갈린다 — §2.6(349행)이 실측한 대로 Win 참조 해가 정차 28 = 한도 28 **경계 위**라 1 차이가 가능/불가를 뒤집는다.
권고 — 문구 분리: "경로의 첫 고객 방문은 +1" 한 문장을 §7.4에 명시.

### [D1] docs/domain-design.md:935·939 (§11.1 미배정 reason) — 중

문제 — 미배정 reason은 예시 4종뿐이고, "결과 생성 시 계산해 붙인다"의 **판정 규칙**(어떤 조건에서 어떤 reason인가, 복수 원인이 겹치면 무엇이 이기는가)이 문서 어디에도 없다.
근거 — `grep -n 'NO_COMPATIBLE_VEHICLE\|NOT_PLACED\|reason' docs/domain-design.md` → **935행 1건뿐.** §11.2(949행)는 §11.1을 "결과의 **의미 정본**"이라 선언하지만 reason의 의미 판정 기준이 비어 있다. §11.2가 협의로 미룬 것은 "이름·형태"뿐이다.
증상 — 구현자가 reason 산정 방식을 매번 되물어야 하고, 규칙이 없으니 구현마다 같은 banked Request에 다른 reason이 붙는다 (예: 시간창도 용량도 안 맞는 주문 — TIME_WINDOW_INFEASIBLE인가 CAPACITY인가 NOT_PLACED인가).
권고 — 상위 문서 개정: §11.1에 reason 판정 규칙을 적거나, "Stage 6에서 확정" 같은 명시적 유예 표기를 남긴다.

### [D1] docs/domain-design.md:554 (§6.2 hard 행) — 경

문제 — hard 행이 "…maxStop·maxDrive **등 전부** 충족"으로 열려 있어("등") hard 제약의 전수 목록이 없고, 축 이름이 canonical 필드명(`maxStopCnt`·`maxDriveTime`·`maxDriveDist`, 223행)과 달라 "maxDrive"가 시간·거리 중 무엇인지(또는 둘 다인지) 안 보인다.
근거 — 554행 인용 vs 223행 "`maxStopCnt`, `maxDriveTime`(초), `maxDriveDist`(m)".
증상 — Stage 3·5가 각자 "등"의 범위를 다르게 잡으면 hard 판정이 갈리고, maxDrive를 시간 한 축으로만 읽으면 maxDriveDist 검사가 조용히 누락된다.
권고 — 문구 교정: "등"을 없애고 canonical 필드명으로 전수 나열 (결함 #1의 §10.2 개정과 같은 목록을 쓴다).

### [D2] docs/domain-design.md:818 (§8.3) — 경

문제 — "비교기 자체가 사전식 하나뿐이므로 **가중합 비교기를 만들 수 없다** — 관례가 아니라 구조다"는 성립하지 않는 단언 — profile이 축 하나에 `w1·a + w2·b`를 담으면 사전식 비교기 그대로 가중합 비교가 된다. 구조가 막는 게 아니라 규칙(817행 MUST NOT)이 막는 것이다.
근거 — 804행 "score는 **profile이 소유**하는 축의 순서 있는 목록" — 축의 내용은 구조가 제한하지 않는다. §13 체크리스트 15번("여러 축을 한 숫자로 뭉개는 비교가 없는가")이 별도 검토 항목으로 존재하는 것 자체가 구조로 못 막는다는 방증이다.
증상 — 리뷰어가 "구조가 막아 주니 검토 불필요"로 읽어 축을 뭉갠 profile을 통과시킨다 — 체크리스트 15번을 무력화하는 문장이다.
권고 — 문구 교정: "비교기는 하나지만 축 구성으로 가중합을 흉내 낼 수 있으므로 리뷰 대상(체크리스트 15)"으로 바꾼다.

### [D1] docs/domain-design.md:640-641 (§7.1 절차 6) — 경

문제 — 절차 6 "hard 검사"가 다섯 축(용량·시간창·근무창·차고 창·한도)을 나열하지만 괄호가 그중 넷을 다른 절차(2·7·0·8)로 돌려, **이 절차가 실제 판정하는 것(용량·한도)이 문장에 직접 없다.** 한도의 판정 시점(방문마다 누적 검사인지 경로 종료 시 1회인지)도 미명시다.
근거 — 640~641행 인용 + 226행 "`maxDriveTime`·`maxDriveDist`·`maxStopCnt`는 **경로 전체 합계**의 한도".
증상 — 시간창을 절차 6에서 한 번 더(다른 식으로) 판정하는 중복 구현이 나오거나, 탐색과 재검증이 한도 검사 시점을 다르게 잡는다 (경계 포함 규칙이라 최종 판정은 같지만 재작업 유발).
권고 — 문구 분리: "이 절차가 새로 판정하는 것은 용량·한도(경로 누적)뿐"으로 명시.

### [D1] docs/domain-design.md:737-748 (§7.3 대기 공식) — 경

문제 — customerWaitingTime 합산식이 방문마다 `(departure − serviceEnd)`를 쓰는데, **endDepot 없는 경로의 마지막 방문**은 절차 7("다음 이동을 통째로 담는")이 적용될 다음 이동이 없어 departure가 미정의다.
근거 — 642행(절차 7) vs 647행 "endDepot 없음 : routeEnd = 마지막 serviceEnd".
증상 — 마지막 항을 0으로 두지 않는 구현에서 항등식 `routeOperationalTime = routeEnd − spanStart`(748행)가 깨져, 문서가 "가장 싼 검사"로 내세운 대조가 오탐을 낸다.
권고 — 문구 교정: "후속 이동이 없는 마지막 방문의 departure = serviceEnd" 한 줄 추가.
