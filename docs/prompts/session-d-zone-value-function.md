# 세션 D — 존 배정 DP의 값 함수 재설계 (설계안 작성까지)

브랜치 `stage-05-verify`, 커밋 `912e5b9` 이후에서 시작한다.
**이 세션의 산출물은 설계 문서 한 편이다 — 운영 코드는 고치지 않는다.**

## 왜 이 작업을 하는가 (발단)

존 배정 DP(`ZoneQuotaAllocation`)가 매기는 값이 **2단계(존 내부 적재)가 성공할지를 보지 못한다.**
그 결과 DP 점수가 완전히 동점인 두 배정이 최종 배차에서 미배정 0건과 2건으로 갈렸다. 아래가 그 실측이다.

### 현 값 함수 (`ZoneQuotaAllocation.value`, 2026-09-05 디스크)

```java
/** 존 전이 하나의 값 (부족, 낭비, Σs) — s에 든 유형만 합한다. */
static long[] value(Demand demand, List<VehicleType> types, int[] s) {
    // capacity = Σ s[t] × maxVolume(t),  used = Σ s[t]
    boolean covers = demand.covers(s);
    long shortage = covers ? 0L : Math.max(1L, demand.totalVolume - capacity);
    long waste    = covers ? capacity - demand.totalVolume : 0L;
    return new long[] {shortage, waste, used};
}
```

전 존 합을 사전식으로 비교한다 — `(Σ부족, Σ낭비, Σ대수)`.

### 실측 (실물 fixture `data/win_poc_case_floor.json`, 주문 452·차량 31·차종 6·존 11)

`MAX_FRONTIER_LEAVES`를 419만(4,194,304, 현행)과 26만(262,144)으로 바꿔 돌린 대조다.

| | 419만 (절단 없음) | 26만 (ZONE_29·ZONE_17 절단) |
|---|---|---|
| DP 값 `(부족, 낭비, 대수)` | `(0, 12290, 31)` | `(0, 12290, 31)` — **완전 동점** |
| ZONE_29 배정 | V028·V029(14,000) + V030·V031(17,640) = **4대** | V006(4,900) + V021·V022(10,150) + V030·V031(17,640) = **5대** |
| ZONE_29 여유 | 2,870 (조각: 240·570·1,470·590) | 470 (조각: **80·100·90·110·90**) |
| **최종 미배정** | **0건** | **2건** — WIN_6836(부피 240)·WIN_6627(부피 160) |

- 두 배정은 **DP 점수가 같다.** 26만이 고른 쪽은 ZONE_29만 놓고 보면 낭비가 70(0.116%)뿐이라
  **현 값 함수 기준으로는 오히려 우수하다.** 낭비 2,800을 ZONE_18(3,470)·ZONE_24(2,690)로 옮겼을 뿐이라
  전 존 합이 같아진다.
- 미배정 2건의 인과: 여유 총량 470은 필요량 400보다 크지만 **다섯 조각으로 흩어져 한 조각 최대가 110**이라
  240도 160도 들어갈 자리가 없다. 용량 부족이 아니라 **파편화**다.
- WIN_6836(240)이 거절된 사유 — 존 bin 5대 전수: V006은 부피 여유 930으로 유일하게 넉넉했으나
  **17개 위치 전부 `TIME_WINDOW`**(화물 창 `[20700, 48600]` 안에 방문이 47,616까지 차 있어 꼬리 여유 984초,
  서비스 300초 + 우회가 창을 넘긴다). 나머지 4대는 전부 `CAPACITY_VOLUME`.
  → **부피가 남은 유일한 차는 시간에 막혔고, 시간이 되는 차들은 부피가 없었다.**
- WIN_6627(160)은 그 존 87건 중 **부피 최소**라, leftover의 1-1 교환이 요구하는 `volume(q) < volume(r)` 후보가
  **0건**이다 — 교환 규칙이 구조적으로 가장 작은 요청을 도울 수 없다.
- 419만에서는 V006 같은 작고 시간이 빡빡한 차가 이 존에 배정되지 않았고, 14,000짜리 두 대가
  부피 여유와 정차 여유(4대×28=112 ≥ 87)를 함께 줘서 두 건이 각각 V029·V028에 들어갔다.

### 그래서 무엇이 결함인가

**1단계는 여유(낭비)를 없애는 것을 잘한 일로 채점하고, 2단계는 여유가 있어야 성공한다.**
여유는 시간창·정차 한도·순서 제약을 흡수하는 자원인데 값 함수는 그것을 손실로만 센다.
그 결과 최종 품질이 값 함수와 연결되지 않아, 열거 순서·예산 값·동률 갈림 같은 것이 답을 좌우한다.

`MAX_FRONTIER_LEAVES = 4,194,304`에 독립 근거가 없다는 것(실물 최대 존 ZONE_29가 2,348,844잎 = 56%를 써
여유 1.8배)과, `Allocation.truncated`가 `ZoneQuotaAllocation` 밖에서 읽히지 않는다는 것도
같은 뿌리에서 나온 증상이다 — **이 세션은 뿌리를 다룬다.**

## 설계안이 반드시 답해야 할 것

1. **여유를 무엇으로 셀 것인가.** 지금은 `capacity − 수요`(부피)뿐이다. 2단계 성공을 좌우한 것은
   부피 여유의 **총량이 아니라 최대 조각**이었고, 시간창과 정차 한도도 함께 걸렸다.
   축을 바꿀지, 더할지, 사전식 순서를 어떻게 둘지.
2. **1단계가 2단계를 얼마나 알아야 하는가.** 값 함수는 존 단위 요약만 본다(`Demand`).
   시간창·경로 순서는 2단계에 가야 드러난다. **어디까지를 1단계가 근사할 수 있는지**의 경계를 그어라.
3. **정차 한도와 무게.** `maxNeed`는 부피·무게·정차를 모두 보는데 `value`는 부피만 본다.
   이 비대칭이 의도인지, 실측 근거가 있는지.
4. **T52가 깨진다면 어떻게 할 것인가.** 값 함수를 바꾸면 실물 답이 바뀔 수 있다. T52는
   "개정 전과 같아야 한다"는 회귀 시험이므로, **기대값을 갱신할 조건**을 설계가 미리 정해야 한다
   (더 좋아지면 갱신 / 같아야 함 / 사람이 판정 — 셋 중 무엇인지와 그 근거).
5. **과적합 방지.** `MAX_FRONTIER_LEAVES = 4,194,304`가 실물 fixture 하나에 맞춰 정해진 전례다.
   같은 실수를 반복하지 않으려면 무엇으로 검증할지(합성 변형·`zoneId` 제거 변형·차종 다양화 등)를 §에 적어라.
6. **비교 프로토콜.** 개정 전후를 무엇으로 비교할지. H25 설계 §8이 쓴 재료(①실물 ②`zoneId` 제거
   ③T25 합성 변형)가 이미 있고, 그때 H23은 실물에서 미배정 0·31대였다.
7. **범위 밖을 명시.** 아래는 이 설계가 **다루지 않는다**고 적어라(별건으로 남긴다):
   - 1단계↔2단계 되먹임(2단계 실패를 1단계로 돌려보내 재배정)
   - 1-1 교환 규칙의 `volume(q) < volume(r)` 제약(WIN_6627이 구제 불가인 원인)
   - `MAX_FRONTIER_LEAVES` 값의 재산정과 `truncated` 노출 범위
   이 셋은 값 함수를 고친 뒤 다시 재야 판단이 선다.

## 규칙

- **운영 코드·계약 문서를 고치지 않는다.** 산출물은 `docs/implementation/`의 설계안 1편과,
  근거로 붙일 실측뿐이다. 계약 개정은 **목록으로만** 적는다(구현 세션이 반영한다).
- 근거용 실측이 필요하면 임시 probe를 써도 되지만 **끝나면 반드시 원상복구**하고,
  `git status --short`가 `?? docs/prompts/`만 남는 상태로 끝내라.
- 번호 대역: **T는 T59부터, X는 X35부터** 쓴다. (T58·X29까지 계약 문서가 사용 중이고,
  폐기된 H25 문서가 T53~T56·X29~X34를 문면에 남기고 있다 — 배정 전에 `grep`으로 재확인할 것.)
- 문서가 정하지 않은 것만 묻는다. **해석이 둘이면 둘 다 적고 Q로 남긴다** — 조용히 한쪽을 고르지 않는다.
- 값 함수의 대안을 낼 때는 **실측으로 뒷받침하거나, 뒷받침이 없으면 없다고 적는다.**
  "이러면 좋아질 것이다"를 근거 없이 문서에 남기지 않는다.
- 문서·용어는 한국어이고 기존 표기를 그대로 쓴다(`Request`/존/프론티어/부족/낭비/덮개/재검증).
