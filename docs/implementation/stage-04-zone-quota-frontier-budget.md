# Stage 4 — 존 배정 DP 프론티어 열거의 잎 예산·절단 규칙 재설계

## 0. 한 장 요약

**왜.** 존당 잎 예산 `MAX_FRONTIER_LEAVES`(4,194,304)는 "열거 범위 R마다 따로 열거해 memo하는" 구조 위에 **선착순**으로 배분된다.
그래서 실물 fixture의 ZONE_29는 서로 다른 R 5,040개를 각각 열거해 **2,348,844잎**을 쓰는데, 층의 모든 상태를 덮는 상자 하나로
**한 번** 열거하면 **1,933잎**으로 같은 프론티어가 전부 나온다(§1.3 — 1/1,215). 예산이 바닥나면 뒤 상태는 빈 집합 (c)만 받아
좋은 전이가 **후보에 없다**(X39): 26만 예산에서 실물 답이 미배정 2로 깨지고(값 함수 문서 §1.4), 차종 31종 변형에서는 존마다 상태
26,024개 중 **99%**가 (c)뿐이라(§1.2) 답이 값 함수가 아니라 절단 순서로 정해진다(값 함수 문서 §5.5 ③).

**무엇.** 프론티어를 **존당 1회 공유 열거**로 바꾼다 — memo와 선착순 배분을 없앤다.

| # | 개정 | 근거 (§2 실측) |
|---|---|---|
| ① 공유 열거 | 존 z를 시작할 때 상자 `B_t = min(대수_t, maxNeed(z,t))`로 **한 번** 열거하고 (c)·(a)·"(b) 후보(확장 마스크 포함)"를 사전식 정렬 배열로 보관. 상태 R마다 접두 범위 탐색으로 `s ≤ R`을 뽑고 (b)는 **R 기준으로 재판정**한다 | 방문 집합이 상자에 단조이고 분류가 `covers`에만 의존하므로 **R마다 따로 열거한 것과 같은 집합**(§2.5 논증). 실물·A·C·D·E 전부 현행 419만과 **동일 답**, 26만 예산에서도 동일(현행 26만은 base 2·A 25·E 7 미배정). D는 절단 없이 완주(현행은 절단) |
| ② 잎 예산 | 그 한 번의 열거에만 걸린다. 값 4,194,304 **유지**(Q1) — 근거 문장을 "실물 소비의 1.8배"에서 "메모리·시간 상한"으로 바꾼다 | 실물 소비 1,933 · D 2,520 · 31종 ZONE_29만 4,194,304에 닿는다(16,777,216이면 11,900,170으로 완주, 답 동일) |
| ③ 후보 상한 | 상태 하나가 받는 후보 수 상한 `MAX_FRONTIER_CANDIDATES`(정렬 접두, Q2) — 프론티어 자체가 큰 입력(31종)에서 전이 수(상태 × 후보)를 묶는다 | 31종에서 정확 프론티어는 상태당 수천 개라 DP가 176초(현행 23초 — 현행이 빨랐던 이유는 99%가 굶주려서다). §2.6 표 |

**고치지 못하는 것.** 31종처럼 프론티어가 **본질적으로 큰** 입력에서는 후보 상한이 곧 근사다 — 상한 안에서 정렬 접두(큰 차 조합 우선)를
받는 것이지 값 순이 아니다. 상태 폭 제한의 정렬(X38)·값 함수·2단계는 손대지 않는다(§8).

## 1. 현상 진단

### 1.1 현 규칙 (scaling §2.7 · heuristics §5 공통 블록)

```text
존 z 시작: budget = MAX_FRONTIER_LEAVES
상태마다 R_t = min(남은_t, maxNeed(z,t)); memo[R]이 없으면 frontier(R, z, cap = max(1, budget)) 열거 → budget −= 잎
  cap에 닿으면 열거 순서 접두만 남기고 truncated. budget ≤ 0이어도 cap ≥ 1이라 (c)는 나온다 (X29)
```

memo는 "같은 R이면 같은 프론티어"라는 재량 최적화(2026-09-04)였고, 잎 예산은 그 memo 항목들이 **선착순**으로 나눠 쓴다.

읽는 법:
- 31종에서는 유형마다 대수가 1이라 **상태마다 R이 다르다**(memo 항목 = 상태 수). 존당 예산을 26,024개가 나누면 상태당 161잎인데
  선착순이라 앞 147개가 다 쓰고 나머지 25,876개는 (c)뿐이다. DP는 "이 존을 건너뛰는" 전이밖에 못 보고, 그 상태들은 부족 > 0으로
  다음 층에서 밀린다 — 값 함수가 무엇이든 마찬가지다(값 함수 문서 §5.5 ③의 원인이 이것이다).
- 실물에서도 ZONE_29·17이 예산의 56%·31%를 쓴다. 지금은 안 잘리지만, 차량 2대만 더 있으면(D) ZONE_29가 잘린다 —
  실물 규모 바로 옆이다.
- "(c)뿐인 상태" 열의 실물 47·1,354는 **정상**이다 — 남은 차량으로 그 존을 덮을 수 없는 상태(부족 > 0)이고 예산과 무관하다.
  아래 §2의 지표는 이 몫을 뺀 것이다.

### 1.3 재열거의 낭비 — 방문 집합은 상자에 단조다

`enumerate`는 유형 순서로 대수를 0..R_t 늘리며 재귀하고, 뒤 유형이 0인 채로 이미 덮이면 그 유형을 더 늘리지 않는다.
이 가지치기는 **s에만 의존하고 R에는 의존하지 않는다** — 그래서 `R ≤ B`이면 `visited(R) = visited(B) ∩ {s ≤ R}`이다.
분류 (a)·(c)도 `covers(s)`에만 의존한다. (b)만 R을 본다("확장 가능한 모든 t에서 덮는다"의 "확장 가능"이 `R_t > s_t`다).

그러므로 층의 모든 상태를 덮는 상자 B로 **한 번** 열거하면 모든 R의 (a)·(c)가 그 안에 있고, (b)는 벡터마다 "어느 확장이 덮는가"의
마스크를 함께 저장하면 R마다 재판정할 수 있다(§2.5). 실측:

| 입력 | 존 | 현행 소비 (memo 합) | 상자 1회 열거 | 배율 | 보관 벡터 (a) / (b) 후보 |
|---|---|---:|---:|---:|---|
| 실물 | ZONE_29 | 2,348,844 | **1,933** | 1,215× | 298 / 618 |
| 실물 | ZONE_17 | 1,288,845 | < 1,000 | > 1,000× | — |
| D | ZONE_29 · ZONE_17 | 4,195,705 · 2,658,911 | 2,520 · 1,115 | 1,665× · 2,385× | 400/797 · 54/661 |
| ③ 31종 | ZONE_29 | 4,216,667 (소진) | 4,194,304 (소진 — 16,777,216이면 11,900,170으로 완주) | — | 657,785 / 716,992 |
| ③ 31종 | ZONE_17 · 21 · 18 | ≈ 4,210,000 (소진) | 1,659,702 · 213,937 · 70,126 | 완주 | 34,161/1,424,256 · 41,527/23,610 · 14,815/18,534 |

memo가 예산을 **R 수만큼 곱해** 쓰고 있었다. 31종에서도 대부분의 존은 상자 1회 열거가 예산 안에 든다 — ZONE_29(87건, 가장 큰 존)만 넘친다.

### 2.2 공평 분할 — 기각

선착순은 없애지만 재열거 낭비(결함 B)는 그대로다. 그래서 (i) 실물 419만에서 ZONE_29가 **불필요하게 잘린다**(2,266,379잎 — 총량은
충분한데 호출당 배분이 모자라서) → T52의 `truncated == false`가 깨진다. (ii) A@26만에서 19로 정확 답(14)에 못 미친다.
31종 3 미배정·17초는 좋지만 공유 정확판이 같은 3을 낸다.

### 2.3 덮개 대체 — 기각

실물·E@26만은 회복하지만 **31종에서 15**(현행 4)로 크게 나쁘다. greedy 덮개는 큰 차부터 쓰고 상태마다 하나뿐이라, 굶은 상태가
전부 "큰 차를 먹는" 같은 전이를 받아 뒤 존이 굶는다. 후보가 없는 상태에 후보를 하나 주는 것은 답이 아니다 — 후보를 **골고루** 주는
것이 답이고 그것이 공유 열거다.

### 2.4 공유 열거 (B 기준 (b)) — 기각 (정확판이 같은 비용에 가능)

답은 정확판과 같았지만 두 가지 문제가 있다. (i) 상태별 필터가 목록 전체를 훑어 31종에서 750초. (ii) (b)가 상자 B 기준이라
`R_t = s_t < B_t`인 방향의 "확장해도 못 덮음"을 못 본다 — 예: 큰 차 1대가 있어야만 덮이는 존(Hall)에서 상태 R = (작은 차 3, 큰 차 0)에
대해 B 기준 (b) `(3, 0)`이 후보로 남는다. 실을 수 없는 작은 차 3대를 태우는 부분 배정이고, R 기준 정의에서는 (b)가 아니다.
못 덮는 존(X21)에서만 드러나는 차이지만 계약의 (b) 정의를 바꾸는 셈이라 채택하지 않는다.

### 2.5 공유 열거 정확판 — 채택 권고

```text
존 z 시작:  B_t = min(대수_t, maxNeed(z,t))                       ← 층의 모든 R을 덮는 상자 (R_t = min(남은_t, maxNeed) ≤ B_t)
  F_z = enumerate(B, z, MAX_FRONTIER_LEAVES)                      ← 존당 1회. 열거·가지치기·cap·truncated는 현 enumerate 그대로
    잎 s 분류:  s = 0 → (c) 보관
               covers(s) ∧ ¬covers(s − e_min) → (a) 보관 · covers(s) 그 외 → 버림
               ¬covers(s): mask(s) = { t : B_t > s_t ∧ covers(s + e_t) } — mask ≠ ∅면 (b) 후보로 mask와 함께 보관, ∅면 버림
    보관 벡터를 사전식(유형 index 0부터, 대수 ASC) 정렬 배열로
상태마다:  R_t = min(남은_t, maxNeed(z,t))                        (현 계약 그대로)
  후보(R) = { s ∈ F_z : s ≤ R ∧ [ (c) ∨ (a) ∨ ( (b) 후보 ∧ ∃t R_t > s_t ∧ ∀t (R_t = s_t ∨ t ∈ mask(s)) ) ] }
    = 정렬 배열 위 접두 범위 탐색 — 유형 t에서 s_t ≤ R_t인 구간만 내려간다 (구간 경계는 이진 탐색)
  전이·값·동률·폭 제한은 무변경
존이 끝나면 F_z를 버린다
```

**왜 R마다 따로 열거한 것과 같은가.**
1. `visited(R) = visited(B) ∩ {s ≤ R}` — 가지치기가 s에만 의존한다(§1.3). cap이 걸리지 않았을 때다.
2. (a)·(c)는 `covers(s)`만 본다 → 같은 판정.
3. (b)_R(s) ⇔ `¬covers(s) ∧ ∃t R_t > s_t ∧ ∀t (R_t = s_t ∨ covers(s + e_t))`. `R_t > s_t`이면 `B_t > s_t`라 그 t의 비트가 mask에
   계산돼 있고, `B_t = s_t`이면 `R_t = s_t`라 조건이 비어 있다. 그러므로 mask로 재판정한 결과가 정의와 같다. mask = ∅인 비덮개는
   어떤 R에서도 (b)가 아니므로 버려도 된다.
4. cap이 걸렸을 때: 모든 상태가 **같은 접두**를 본다(선착순 없음, X40). 접두는 열거 순서(유형 index ASC · 대수 ASC의 DFS — 마지막
   유형, 즉 가장 큰 차부터 변한다)의 앞부분이다 — 큰 차 조합의 최소 덮개가 먼저 나온다.

**비용.** 열거 1회 ≤ `MAX_FRONTIER_LEAVES`잎(현행과 같은 상한, 소비는 1/1,000). 정렬 O(n log n), n = 보관 벡터 ≤ 잎.
추출은 상태당 O(|후보| × T + 분기 × log n) — 실물 ZONE_29 상태 8,635개 합계 **16 ms**, 31종 ZONE_21 26,024개 합계 9.9초(후보가 많다).
전이 수 = Σ 상태 × |후보| — 상한은 현행과 같지만 현행은 굶주림으로 작았다 → §2.6.
메모리: 존 하나의 보관 목록 ≤ 잎 × (16 + 4T + 8) B. 실물 ≈ 1,000벡터 · 31종 ZONE_29 1.37M벡터 ≈ 215 MB(419만), 3.7M ≈ 580 MB(1,678만).
scaling §5의 상한(31종 587 MB)과 같은 급이고 존이 끝나면 버린다 (X43).

### 2.6 후보 상한 — 31종의 전이 수

정확 프론티어는 31종에서 상태당 후보가 수천 개라 DP가 176초다(현행 23초). 시간을 묶는 자리는 **상태 하나가 받는 후보 수**다 —
정렬 접두 K개에서 멈춘다(작은 유형 대수가 0인 벡터, 즉 큰 차 조합부터). (c)는 사전식 첫 원소라 항상 포함된다.

| 31종 · 후보 상한 K | DP 소요 | H23 score | 상한에 닿은 상태 (존) | 전이 수 (ZONE_21) |
|---|---:|---|---|---:|
| 없음 (정확) | **176 s** | [3, 31, 4,590,848, 1,018,140] | — | > 106M |
| 4,096 | 123 s | 동일 | ZONE_21 전부 · ZONE_18 1,650 | 106,594,304 |
| 1,024 | **50 s** | 동일 | ZONE_21·18 전부 · ZONE_16 6,270 · ZONE_15 전부 | 26,737,664 |
| 256 | 20.8 s (≈ 현행 23 s) | 동일 | 대부분의 존 전부 | 5,870,848 |
| 현행 (참고) | 22.7 s | [4, 31, 4,881,329, 1,016,210] | (굶주림 99%) | — |

- 답은 K와 무관하게 같았다 — 정렬 접두(큰 차 조합)가 DP가 실제로 고르는 후보를 담고 있다는 뜻이지만 입력 하나의 실측이다.
- **실물 규모에서는 K = 1,024가 닿지 않는다** — 실물·A·B·C·D·E 전부 상한 발동 0, `truncated == false`, 배정이 운영 `allocate()`와
  **동일**(`vehiclesByZone` 비교). K = 256은 실물 ZONE_29에서 상태 585개(D는 1,772개)를 자른다 — 답은 그대로지만 `truncated == true`가
  되어 T52가 깨진다(실물 상태당 후보 최대 526, scaling §2.7). 그래서 K의 하한은 실물 최대 후보 수 위여야 한다.
- 실물 ZONE_29의 전이 수는 1,160,638(상태당 평균 134)이고 현행과 같다 — 후보 집합이 같으므로.

### 2.7 예산 값 `MAX_FRONTIER_LEAVES`

공유 열거에서의 소비: 실물 1,933 · D 2,520 · 31종 ZONE_29 4,194,304(소진; 16,777,216이면 11,900,170으로 완주하되 답은 같다 —
[3, 31, 4,590,848, 1,018,140]). 값을 바꿀 근거가 두 방향 다 약하다: 줄이면 31종 ZONE_29만 더 잘리고(품질 미실측), 늘리면 메모리 상한이
그만큼 는다. **4,194,304 유지**를 권고하고 근거 문장만 바꾼다 — "실물 최대 소비의 1.8배"가 아니라 **"존 하나의 열거가 도달할 수
있는 잎의 상한 = 시간·메모리 상한(벡터 ≤ 잎)"**. 실물은 이 상한의 0.05%를 쓴다 (Q1).

## 3. 시그니처 변경 (§3.4 대체분)

바뀌는 것만 적는다. 이름은 유지한다.

```java
final class ZoneQuotaAllocation {
    /** 존 하나의 프론티어 열거(존당 1회)가 도달할 수 있는 잎 수 총량 — 시간·메모리 상한 (재량 상수, §2.7). 소진되면 열거 순서 접두만 남기고 근사한다. */
    static final int MAX_FRONTIER_LEAVES = 4_194_304;            // 값 무변경 · 주석 교체
    /** 상태 하나가 받는 후보 수 상한 (재량 상수, §2.6 · Q2). 정렬 접두에서 멈추고 truncated = true. */
    static final int MAX_FRONTIER_CANDIDATES = 1_024;       // Q2

    /** 프론티어 열거 결과 — 무변경 (T49). */
    record Frontier(List<int[]> vectors, int leaves, boolean truncated) {}
    /** 무변경 시그니처 — 구현은 ZoneFrontier.enumerate(range, demand, cap).forRange(range, Integer.MAX_VALUE)로 위임 (T49·T63). */
    static Frontier frontier(int[] range, Demand demand, int cap);

    /**
     * 존 하나의 공유 프론티어 (§2.5) — 상자 box로 1회 열거한 (c)·(a)·(b) 후보(확장 마스크 포함)를 사전식 정렬로 보관한다.
     * forRange(R)는 s ≤ R을 접두 범위 탐색으로 뽑고 (b)는 R 기준으로 재판정한다 — R마다 따로 열거한 것과 같은 집합.
     * 후보가 candidateCap개에 이르면 거기서 멈춘다 (정렬 접두).
     */
    static final class ZoneFrontier {
        static ZoneFrontier enumerate(int[] box, Demand demand, int cap);
        List<int[]> forRange(int[] range, int candidateCap);
        int leaves();
        boolean truncated();                                       // cap에 닿아 열거가 잘렸는가
    }

    // 무변경: MAX_TOTAL_STATES · VALUE_AXES · KEY_ORDER · VehicleType · Zone · Allocation · Component · Demand ·
    //         vehicleTypes · zones · components · maxNeed · value · compare · allocate(problem) · allocate(problem, maxTotalStates)
}
```

- `solveComponent`의 `TreeMap<int[], List<int[]>> frontiers`(memo)와 `leafBudget` 차감 루프가 사라지고, 존 시작에서
  `ZoneFrontier.enumerate(B, demand, MAX_FRONTIER_LEAVES)` 한 번, 상태마다 `forRange(range, MAX_FRONTIER_CANDIDATES)`가 된다.
  `truncated |= zoneFrontier.truncated() ∨ (후보가 상한에 닿음)`.
- `enumerate`·`classify`는 `ZoneFrontier` 안으로 옮기되 열거 순서·가지치기·`Enumeration`(잎 세기)은 그대로다. `classify`가 (b)를
  "B 기준 판정"에서 "mask 계산"으로 바꾼다 — 확장 t마다 `covers(s + e_t)`를 한 번씩 보는 것은 지금과 같은 횟수다(지금은 하나라도
  실패하면 멈추므로 최대 T회, 개정은 항상 T회 — 상수 배).
- 상자 B의 `대수_t`는 그 유형의 **전체 대수**다(성분 시작 상태의 남은 대수 = `types.get(t).vehicles().size()`). 풍부 유형은
  대수 ≥ Σ maxNeed ≥ maxNeed라 B_t = maxNeed_t — 현 R과 같다.
- 예산 주입 오버로드를 **더하지 않는다**(값 함수 문서 §3과 같은 이유). 26만 대조는 이 문서 §1.4의 probe 기록으로 남는다.

## 4. 의사코드 (§5 "공통 — 존 배정 DP" 블록의 프론티어 memo 단락 대체분)

```text
프론티어 열거는 존마다 한 번이다 — 상자 B_t = min(대수_t, maxNeed(z,t))로 열거한 벡터를 존 z의 공유 프론티어 F_z에 보관한다:
  열거 = 유형 순서 재귀 나열(대수 0..B_t, covers가 되는 순간 그 유형에서 중단), 잎 예산 MAX_FRONTIER_LEAVES까지 —
  cap에 닿아 멈췄으면 Allocation.truncated = true (X29 그대로). 자르는 규칙은 열거 순서의 접두다 (모든 상태가 같은 접두를 본다, X40).
  잎 s의 분류: s = 0 → (c) · covers(s) ∧ ¬covers(s − e_min) → (a) · ¬covers(s) ∧ mask(s) ≠ ∅ → (b) 후보 (mask(s) = 덮게 하는 확장 방향)
  F_z는 사전식 정렬 배열.
상태마다 R_t = min(남은_t, maxNeed(z,t)) (무변경). 후보(R) = F_z에서 s ≤ R인 (c)·(a)와, (b) 후보 중
  ∃t R_t > s_t ∧ ∀t (R_t = s_t ∨ t ∈ mask(s))인 것 — 이것이 (b)의 정의 그대로다 (§2.5).
  접두 범위 탐색으로 뽑고, MAX_FRONTIER_CANDIDATES개에 이르면 멈춘다 (정렬 접두 · truncated = true, X42).
전이·값 (부족, 대수, 낭비, 결손)·동률·폭 제한·역추적은 무변경. 존이 끝나면 F_z를 버린다.
종료: 성분당 보관 상태 ≤ MAX_TOTAL_STATES + 존 수 · 존당 열거 잎 ≤ MAX_FRONTIER_LEAVES (1회) ·
  상태당 후보 ≤ MAX_FRONTIER_CANDIDATES ⇒ 전이 ≤ 상태 × 후보 상한 — 루프 상한이 아니라 구조 (§4.3). 기권 없음.
```

## 5. 검증 — 비교 프로토콜 · T52·T58 · 과적합 방지

### 5.1 비교 프로토콜 (값 함수 문서 §5.3 형식)

재료마다 **개정 전(현행)과 개정 후**를 같은 실행에서:

| 입력 | 보는 것 | 예측 (probe §2.1) |
|---|---|---|
| ① 실물 fixture | 본 비교 — score·`truncated`·DP 소요 | 동일 `[0, 31, 4,194,052, 1,004,144]` · false · ≈ 0.7 s |
| ② 변형 A·C (못 덮는 존) | (b) 재판정의 정확성 | 동일 |
| ③ 변형 D (33대) | 절단이 사라지는가 | 동일 답 · `truncated` true → **false** |
| ④ 변형 E·실물·A @ 26만 | 예산 의존성 (probe에서만 — 오버로드 없음) | 전부 419만 답 |
| ⑤ 31종 (T58) | 완주·소요·미배정·후보 상한 발동 | 미배정 4 → 3, 소요는 Q2의 K에 따라 (§2.6) |
| ⑥ 손조립 오라클 (T62) | 모든 R ≤ B에서 `forRange(R)` = 정의 그대로의 brute force | 집합 동일 |

| ①이 달라짐 | **구현 결함** — §2.5의 논증이 틀렸거나 정렬·마스크 구현 오류. 원인부터 |
| ②에서 달라짐 | (b) 재판정 결함 후보 — T62를 그 입력 형태로 넓혀 원인부터 |

### 5.2 T52·T58 취급

- **T52는 무변경이 채택 조건**이다 — 이 설계는 실물 답을 바꾸지 않아야 한다(§2.5 논증 + probe 동일 답). 달라지면 갱신이 아니라
  설계 결함이다(값 함수 문서 §5.4와 반대 방향).
- **T58 문면 갱신** — "완주·유효·결정적·truncated"는 그대로, 소요 실측치와 미배정 수(H23으로 돌린 값 3)를 새로 적는다.
  31종은 여전히 `truncated == true`다(ZONE_29 예산 소진 + 후보 상한).

### 5.3 과적합 방지

1. 상수는 둘뿐이고 값이 fixture에서 나오지 않는다 — `MAX_FRONTIER_LEAVES`는 메모리·시간 상한(§2.7), `MAX_FRONTIER_CANDIDATES`는
   전이 수 상한(§2.6 — 실물은 상한의 1/8 이하라 닿지 않는다).
2. 정확성 논증(§2.5)이 입력과 무관하다 — T62 brute-force 오라클이 손조립 입력에서 이를 고정한다. 여기에는 B 기준 (b)와 R 기준 (b)가
   갈리는 입력(§2.4의 Hall 예)을 반드시 넣는다.
3. 변형 A·C·D·E와 26만 대조군이 §5.1의 채택 조건이다.
