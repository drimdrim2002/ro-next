# Stage 8 — 벤치마크 비교

win_poc 입력에 대한 우리 솔버의 지표를 기존 엔진(Win)의 결과와 나란히 놓고 비교하고,
필요한 만큼 탐색 파라미터를 조정한다. 주 근거: [Master §5](../master-design.md)
"1차 성공 기준 … 이후 기존 엔진(Win) 결과와 지표 비교", [Plan §0·Stage 8](../implementation-plan.md).

**이 문서의 성격**: Plan Stage 8은 "비교 절차와 수치는 이 단계에서 기록한다 (사전 확정하지 않음)"
이다. 따라서 이 문서는 **비교를 수행하는 절차와 기록 양식**만 설계한다. 목표 수치·허용
오차(예: "거리 5% 이내")를 만들지 않으며, 실측 수치는 실행 시점에 §4의 기록 문서에 남긴다.

이 Stage는 저장소에 남는 새 코드가 없다 — §3.1의 CSV 재생 도구는 벤치마크 실행 시점에
만들었다 버리는 일회성 절차이고, 본 문서에는 그 절차 서술만 둔다. 파라미터 조정도 Stage 4가
재량으로 열어 둔 값·연산자의 범위 안에서만 움직인다 (경계 변경 없음). 산출물은 §4의 기록
문서(benchmark-results.md) 하나다.

## 2. 비교 대상 지표의 정의와 대응

우리 쪽 값은 전부 result.json(Stage 6 §5 wire, 의미는 Domain §11.1)에서 나온다.
이 값들은 탐색 보고값이 아니라 **재검증이 재계산한 값**이다 (Stage 5 N4) — 별도 계측
코드 없이 결과 파일만 읽으면 된다. Win 쪽 값은 CSV에 없다 — `data/alns_result.csv`는
배정과 순번뿐이므로 Win 지표는 §3.1의 재생이 **우리 계산 규칙으로 직접 산출**한다.
두 열이 같은 정의·같은 이동표에서 나오므로 별도의 "매핑 확정" 절차가 필요 없다.

| Plan Stage 8 축 | 우리 값 (result.json) | 뜻 | Win 대응 |
|---|---|---|---|
| 미배정 | `metrics.unassignedCount` | 재검증 통과 해의 미배정 주문 수 (`unassigned[]` 길이와 일치) | 재생으로 산출 — CSV 사실만으로 **0** 확정 (452건 전부 배정) |
| 차량 수 | `metrics.usedVehicleCount` | 방문이 1개 이상인 경로 수 (빈 경로·미사용 차량 제외 — Stage 3 §4.1) | 재생으로 산출 — CSV 사실만으로 **31** 확정 (V001~V031 전부 사용) |
| 거리 | `metrics.totalDistanceMeter` | 전 경로 실제 주행 arc 합, 정수 meter. oneway·endDepot 부재면 복귀 arc 없음 (Domain §7.4) | 재생으로 산출 — 같은 이동표라 단위·복귀 arc 논점이 없다 |
| 시간 | `metrics.totalRouteOperationalTimeSec` | **주행+고객대기+차고대기+서비스+휴식** 합 (Domain §7.3) | 재생으로 산출 — 같은 §7.3 정의 (아래 참고) |

**시간 축 참고**: 예전 우려는 "Win이 넘겨줄 시간 숫자가 순수 주행인지 대기 포함인지
모른다"였다. 입수된 CSV에는 시간 숫자가 아예 없으므로 이 우려는 사라졌다 (§9 Q3 해소) —
양쪽 모두 우리 정의(대기·서비스 포함 운행 시간)로 계산된다. 보조 값
**Σ `routes[].driveTimeSec`(순수 주행 합)** 은 차이 원인 분석용으로 계속 기록한다 —
우리 쪽은 result.json 합산, Win 쪽은 재생이 채운 `RouteFacts.driveTimeSec` 합산으로,
새 metric 타입을 만들지 않는다.

**함께 기록하는 보조 값** (비교 축은 아니지만 차이 원인 분석에 필요):

- `unassigned[]`의 **사유 분포** (4종 카운트: NO_COMPATIBLE_VEHICLE / CAPACITY /
  TIME_WINDOW_INFEASIBLE / NOT_PLACED — Stage 5 §4.3)
- Σ `routes[].driveTimeSec` (위), 경로당 방문 수 최댓값 (maxStop 28 대비 여유 확인)

## 3. 비교 실행 절차

공식 기록 실행은 **배포 환경**(Stage 7 §4로 배포된 서비스, 실제 S3)에서 한다 — Stage 7
DoD(V6)와 같은 경로라 별도 준비가 없다. 로컬(local profile) 실행은 파라미터 사전 탐색용으로
허용하되, §4 표에 환경을 구분해 적는다.

```text
1. 선행 확인   P1~P3 (§1). 배포돼 있는 이미지의 커밋 해시를 확인해 둔다.
2. 조건 확정   이번 실행의 조건을 §4 표의 열 그대로 먼저 적는다: 커밋, seed
              (기본 0 — Stage 6 §1.1), 시간 한도(fixture의 Termination.secondsSpentLimit
              = 600초), 기본값과 다르게 바꾼 파라미터 목록 (§5).
3. (필요 시) 재배포   파라미터를 코드·환경변수로 바꿨다면 Stage 7 §4 절차 2~6으로 재배포.
              **진행 중인 solve가 있는 동안은 배포하지 않는다** — 배포·재시작은 진행 중
              풀이를 소실시킨다 (Stage 7 E2).
4. 실행       win_poc_case_floor.json POST → 상태 폴링으로 DONE 대기(한도 600초, 최대
              ~11분 — Stage 6 T13과 동일) → GET result. FAILED·STALE이면 결과 없이
              원인만 §4 문서의 메모에 남긴다 (실패도 기록 대상이다).
5. 지표 추출   result.json에서 §2의 4개 metrics + 보조 값(사유 분포, Σ driveTimeSec)을
              추출해 §4 표에 한 행으로 기록. solveKey도 같이 적는다 (결과 원본의 손잡이).
6. Win 기준   (최초 1회) §3.1의 재생 절차로 data/alns_result.csv에서 Win의 4개 지표를
              산출해 §4 ②에 근거·위반 내역과 함께 기록한다. 재생에 쓴 커밋도 적는다 —
              양쪽을 같은 계산 규칙으로 쟀다는 근거다.
7. 차이 검토   차이가 크면 §6의 차이 요인 표를 먼저 대조한다 — 특히 미배정 사유 분포에
              NO_COMPATIBLE_VEHICLE·CAPACITY가 보이면 파라미터가 아니라 입력 해석
              (호환성·단위) 문제부터 의심한다.
8. 조정 반복   필요하다고 판단되면 §5의 방식으로 파라미터를 바꿔 2~7을 반복한다.
              모든 실행이 §4 표에 남는다 — 좋은 결과만 골라 적지 않는다.
```

실행 조건의 근거는 두 곳이다 (2026-08-10 갱신):

| 어디에 | 무엇이 | 근거 |
|---|---|---|
| **result.json의 run** | 적용된 **배송정책**과 **탐색 예산**(시간·step·idle 한도·seed)이 각각 따로 | Domain §11.1, Stage 5 §4.1 |
| **§4 표** | 커밋·환경·`AlnsConfig`의 **알고리즘 튜닝** 파라미터(destroy 비율·연산자 구성 등)·종료 사유(실행 로그의 `AlnsRunStats.termination` — run 메타에는 실리지 않는다, Stage 5 §9)·관찰 메모 | 본 문서 |

- 이 분리 덕분에 **"문제는 같고 예산만 달랐다"**를 결과만 보고 판별할 수 있다 —
  배송정책이 같고 `searchBudget`만 다른 두 run은 같은 문제의 서로 다른 예산 실행이다.
  배송정책이 다르면 애초에 **다른 문제**이므로 지표를 나란히 놓으면 안 된다.
- 다만 튜닝 파라미터는 여전히 결과에 남지 않는다. 실행 조건의 완전한 근거는 result.json +
  §4 표이므로, 절차 2(실행 전 기록)를 건너뛰지 않는다.

### 3.1 Win 기준 지표 산출 — CSV 재생 (절차 6의 상세)

`data/alns_result.csv`에 있는 것은 "어떤 주문을(orderNo) 어떤 차량이(vehicleId) 몇 번째로
(stopSeqNo) 방문하는가"뿐이고 지표 숫자는 없다. 그래서 Win의 4개 지표는 **경로를 복원해
우리 계산기로 다시 재는(재생, replay)** 방식으로 얻는다. 이러면 두 엔진의 결과가 같은
이동표(Stage 2 freeze)·같은 시간 규칙(Domain §7)으로 계산되므로, Win 내부 수치를 옮겨 적을
때 생기는 단위·정의 차이 문제가 원천적으로 없다 — 이것이 공정 비교의 핵심이다.

재생 도구는 벤치마크 실행 시점에 만들었다 버리는 **일회성 절차**다 (scratch 테스트·main
메서드 등 형태 재량). 저장소에 코드를 남기지 않으며, 남는 것은 §4 ②의 수치와 위반
내역뿐이다. 절차:

```text
준비   win_poc_case_floor.json → Stage 6 adapter 채움(startDepot=WIN_0) →
      Stage 1 정규화 → Stage 2 freeze → problem.
      우리 실행(앱 접수)과 같은 출발이다. fixture 파일은 고치지 않는다 — multiRotation 1은
      1바퀴라 정규화를 그대로 통과하고, start 키 없음은 adapter가 채운다 (§1 P1 해소,
      Domain §2.4 2026-08-14).

1. 복원 (CSV → 차량별 방문 목록)
   rows = alns_result.csv 파싱
      # 파일 선두에 BOM이 있다 — utf-8-sig 등 BOM을 무시하는 방식으로 읽을 것
   각 행: byVehicle[vehicleId] += (stopSeqNo, NodeId.delivery(RequestId(orderNo)))
      # 전 주문이 배송 전용(방문지 1개)이라 orderNo 하나가 배송 방문 NodeId 하나로 끝난다
   차량마다 stopSeqNo 오름차순 정렬 → List<NodeId> visits (31개 경로, 방문 452개)
   재확인: orderNo 452개 = fixture orderId 452개, 차량 31대, 순번 1부터 연속 (§1 P2)

2. 재생 (경로 → 지표)
   solution = Solution(31개 Route, bank = ∅)        # 미배정 0 — CSV 사실
   Evaluator.evaluate(problem, profiles.resolve(plan.customerId()), solution)
      # 우리 실행과 반드시 같은 profile — 다르면 두 지표를 나란히 놓을 수 없다
   ├─ Feasible(evaluation, score, routes)
   │    → 4개 지표 = evaluation 그대로. unassignedCount=0·usedVehicleCount=31이
   │      CSV 사실과 일치하는지 확인 (어긋나면 복원 버그).
   │      보조 값 Σ routes[].driveTimeSec 도 같이 뽑는다 (§2).
   └─ Infeasible → 아래 위반 처리 방침
```

**위반 처리 방침** (유의점): Win은 다른 엔진이다 — 우리 규칙으로 재생하면 시간창·용량 등
hard 위반이 발견될 수 있다 (예: Win의 시간창 close 기준이 다르면 W6). 이는 비교를 막는
요인이 아니라 **두 엔진의 규칙 차이를 보여주는 기록 대상**이다.

- `Evaluator`는 첫 위반에서 멈추므로, Infeasible이면 경로별로
  `RoutePropagator.propagate(problem, vehicleId, visits)`를 돌려 **위반 경로 전부**를
  나열한다 (경로당 첫 위반의 Violation 종류·위치 at). §4 ②의 위반 표에 기록.
- **거리**는 규칙과 무관하다 — visits 순서대로 `problem.travel()`의 arc 거리를 합산하면
  위반 여부와 상관없이 전 경로 총거리가 나온다 (우리 정의와 동일: 복귀 arc 없음).
- **시간**은 위반 경로에서는 우리 정의대로 산출할 수 없다 — 위반 없는 경로들의 합만
  "부분합"으로 기록하고 그 사실을 비고에 명시한다. 미배정 0·차량 31은 CSV 사실로 확정.

## 4. 기록 양식 — `docs/implementation/benchmark-results.md`

벤치마크 실행 시점에 이 경로로 만든다 (본 Stage 설계 문서와 분리 — 설계는 고정, 수치는

fingerprint·provenance 추적 체계를 만들지 않는다 — 아래 표 한 줄이 실행 조건 기록의 전부다.

**① 실행 기록 표** (실행 1회 = 1행, 시간순 누적):

```markdown
| # | 일시(UTC) | 환경 | 커밋 | seed | 한도(s) | 종료 | 기본값과 다른 파라미터 | 미배정 | 차량 | 총거리(m) | 운행시간(s) | Σ주행(s) | 사유 분포 | solveKey | 비고 |
|---|---|---|---|---|---|---|---|---:|---:|---:|---:|---:|---|---|---|
| 1 | 2026-.. | 배포 | abc1234 | 0 | 600 | TIME_LIMIT | (없음 — 전부 기본값) | | | | | | NP:.. | solves/... | 최초 실행 |
```

- "기본값과 다른 파라미터"는 Stage 4 §3.3 `AlnsConfig.defaults` 기준으로 바꾼 것만 적는다
  (예: `maxDestroyFraction=0.4`, `+ShawRemoval`). 전부 기본값이면 "(없음)".
- seed·한도 열은 result.json의 `run.searchBudget`에서 그대로 옮긴다 — 손으로 다시 적지
  않는다. "종료"(TIME_LIMIT/MAX_STEPS/IDLE_STEPS/IDLE_TIME) 열은 run 메타에 실리지
  않으므로(stats — Domain §11.1, Stage 5 §9) 실행 로그의 `AlnsRunStats.termination`
  (Stage 4 §3.2, 로그·실험용)에서 옮긴다.
  **IDLE_* 로 끝난 실행은 시간을 다 쓰지 않았다는 뜻**이므로, 시간 한도만 늘려도
  개선되지 않는다는 신호로 읽는다 (§5 조정 판단의 입력).
- 환경: `배포` / `로컬`. 공식 비교 대상 행은 배포 환경 실행이다 (§3 서두).
- 사유 분포는 축약 표기 재량 (예: `NP:12 TW:3`).

**② Win 참조값 절**: §3.1 재생으로 산출한 Win 지표(미배정 0·차량 31·총거리·운행시간)와
**근거를 반드시 적는다** — 원본 `data/alns_result.csv`(입수 2026-08-10, 452행 검증은 §1 P2),
재생에 쓴 커밋, 보조 값 Σ driveTimeSec, 시간이 부분합이면 그 사실. 이어서 **재생 위반
내역**을 아래 표로 남긴다 — 위반이 없어도 "없음"이라고 명시적으로 적는다 (확인했다는 기록):

```markdown
| 차량 | 위반(Violation) | 위치(at) | 메모 (우리 규칙 기준 어떤 제약인지) |
|---|---|---|---|
```

**③ 관찰 메모**: 실행 간 비교에서 본 것(변동폭, 조정 효과, 규칙 차이 의심 지점)을
자유 서술로. 회귀 판정 규칙·gate를 만들지 않는다 — 판단은 사람이 표를 보고 한다.

## 5. 파라미터 조정 실험의 진행 방식

무엇을 바꿀 수 있는지는 Stage 4가 확정한 재량 목록이 전부다 (Stage 4 §1 "재량" 행·§3.3·§8).
**고정 경계(pair·XOR·정식 평가 수락·시간 한도 종료 등 Stage 4 §1 "고정" 행)는 실험 대상이
아니다.** 실험 계획을 사전 확정하지 않는다 — 아래는 변경 수단과 진행 원칙만이다.

| 바꿀 수 있는 것 | 어디서 | 변경 수단 | 재배포 |
|---|---|---|---|
| seed | Stage 6 §1.1 `ro-next.solve.seed` | 환경변수 `RONEXT_SOLVE_SEED` (태스크 정의 revision) | 필요 |
| `AlnsConfig` 나머지 (destroy 비율·q 상한, worse 수락 확률, 적응 가중치 segment·ρ·σ) | Stage 4 §3.3 | 코드 기본값 변경 → 새 이미지 | 필요 |
| destroy/repair 연산자 추가 (Shaw/worst removal 등) | Stage 4 §8이 Stage 8 실험으로 이관한 SPI 확장 | 코드 추가 → 새 이미지 | 필요 |
| 초기해 포트폴리오 구성 (**8 → 4 축소**) | [stage-04-initial-solution-heuristics.md](stage-04-initial-solution-heuristics.md) §5·§10 Q1 | 코드 변경 → 새 이미지 | 필요 |
| 초기해 기법별 파라미터 (H3 적재율 0.85, H2 4분위 등급 등) | 〃 §5 (재량) | 코드 변경 → 새 이미지 | 필요 |
| 탐색 시간 한도 | 입력 `Termination.secondsSpentLimit` | 입력 JSON **사본**에서 변경 | 불필요 |

`maxSteps`(최대 step 수 — 종전 이 표의 `maxIterations` 표기는 존재하지 않는 이름이었다,
2026-08-13 교정)는 튜닝이 아니라 **예산 축**이라 이 목록에 두지 않는다 (Domain §2.5.1,
Stage 4 §3.3) — seed·시간 한도처럼 실행 조건으로 `run.searchBudget`에 기록되며, 바꾸려면
Stage 6 §1.1 설정(`ro-next.solve.max-steps` — 환경변수)으로 한다. `idleSteps`·`idleSec`도 같다.

**초기해 22 → 4 축소는 이 Stage가 재료를 내고 사용자가 정한다 (2026-09-02).**
자르는 순서의 권고는 [heuristics-survey §5](stage-04-initial-solution-heuristics-survey.md).
[heuristics 문서](stage-04-initial-solution-heuristics.md) §10 Q1이 이 Stage로 넘긴 미결이다.
재료는 T25가 출력하는 **기법별 소요·미배정 수·score**와 **포트폴리오 총 소요 / `timeLimitSec` 비**이고
(절대 초는 그 자체로 해석되지 않는다 — 이 비가 1에 가까우면 초기해가 ALNS 예산만큼 쓰고 있다는 뜻이다),
여기에 실물 규모 실행에서
"한 번이라도 best로 뽑힌 적이 있는가"(`InitialSolutionResult.heuristicId`)를 더한다 —
한 번도 뽑히지 않은 기법은 계산만 하고 결과에 기여하지 않는다. 이 Stage는 표를 만들 뿐
자르지 않는다. 자를 4개가 정해지면 [Stage Extra E4](stage-extra-deferred-features.md)의
병렬화 트리거가 발동한다.

진행 원칙:

1. **한 번에 한 축**만 바꾼다. 두 가지를 같이 바꾸면 §4 표에서 효과를 분리할 수 없다.
2. Win 대조용 공식 실행은 **fixture 원본 조건(한도 600초) 그대로** 한다. 시간 한도를 바꾼
   실행은 "같은 입력" 비교가 아니므로 표의 비고에 명시하고 Win 대조 결론에 쓰지 않는다.
3. 조정 전후를 같은 seed로 비교하되, 결론 전에 **복수 seed로 변동성을 확인**한다 (§6 W11).
4. seed 기본 정책은 Stage 6 §1.1(고정 0)을 유지한다 — 변동성 실험에서만 바꾸고 행마다 기록.
5. 코드로 바꾼 기본값 중 유지할 것은 실험 종료 시 **커밋 하나로 확정**하고 §4 메모에 근거를
   남긴다. 실험용 임시값을 배포 이미지에 남긴 채 끝내지 않는다.

## 6. 차이 요인 / edge case 표

Win과 지표가 다를 때 파라미터보다 먼저 의심할, 이전 Stage들이 기록해 둔 규칙 해석
차이·주의사항의 집약이다.

| # | 요인 | 내용 | 출처 |
|---|---|---|---|
| W1 | multiRotation | **해소 — 차이 요인이 아니다 (2026-08-10 D1 확정).** 이 칸의 우려는 "Win은 차고 복귀를 쓸 수 있었는데 우리는 못 쓴다면 차량 수·거리가 구조적으로 다르다"였다. **양쪽 다 1바퀴로 확정돼 그 전제가 사라졌다**: `multiRotation`은 바퀴 수이고 fixture 값 `1` = 1바퀴 = 차고 재방문 없음이므로, Win도 우리도 같은 조건에서 푼다. 즉 **fixture를 고치지 않고 그대로 비교**한다.<br>독립적인 뒷받침도 남겨 둔다 (2026-08-10 대조): `data/alns_result.csv`의 Win 참조 해를 차량별로 합산하니 **31대 전부 자기 용량 안**이었다 — 무게 초과 0대·부피 초과 0대(부피 사용률 81~100%, 31대 중 27대가 93% 이상). Win의 답이 **실제로도 전 차량 단일 적재**라, 확정 의미와 관측 결과가 서로 맞는다. 종전 이 칸이 남겨 둔 물음("복귀를 쓸 수 있었는데 안 쓴 것인가, 애초에 못 썼던 것인가")의 답은 **후자**다 | Master §4, Domain §2.5, Plan §2.1 D1 |
| W2 | 시간 지표 의미 | **해소 (재생)**: 우려의 근원은 Win이 넘겨줄 "시간" 숫자의 의미(순수 주행 vs 대기 포함)였는데, CSV에는 시간 숫자가 없고 양쪽 시간 모두 §3.1 재생·우리 정의로 계산된다 — 의미 차이가 생길 자리가 없다. Σ driveTimeSec 보조 값은 분석용으로 유지 (§2) | Domain §7.3 |
| W3 | 입력이 원본이냐 floor본이냐 | **재생으로 거의 해소**: 지표는 양쪽 다 floor 이동표로 재계산되므로 수치 정의 차이는 없다. 남는 것은 해석상 참고 하나 — Win이 원본 소수 표 기준으로 경로를 골랐다면, 우리 표(자)로 잰 Win 경로는 Win 스스로의 셈과 arc당 최대 1m·1s 다를 수 있다 | Stage 1 §4 fixture 근거 |
| W4 | self arc 처리 | **해소 (재생)**: 이 요인은 Win이 계산한 거리 숫자를 받아 적는 경우의 것 — 거리는 우리 표로만 계산하고, 표는 wire의 self arc 값(D=9999·U=0, legacy sentinel)을 읽지 않고 버린 뒤 **D=0·U=0**으로 확정하므로(Domain §4, 2026-08-17 원복 — 2026-08-12의 sentinel 999,000/86,400 강제는 폐기) wire의 9999가 합산에 섞일 일이 없다. 이 fixture는 주문마다 장소가 달라(453 장소 = 452 주문 + 차고 1) 재생 경로가 self arc 자체를 밟지 않아 대각값은 어느 쪽이든 지표에 들어가지 않는다. 참고로 Win 엔진은 같은 좌표의 서로 다른 장소 쌍에 D=0·U=0을 쓴다(행렬 실측) — 원복으로 그 관측과도 일치한다 | Stage 2 E3, Domain §4 |
