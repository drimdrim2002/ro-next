# 세션 10 — 도메인 한계값과 Constants

이 문서는 `master-design.md`와 `domain-design.md`를 개정할 때 적용할 수치 한계값 계약을 정리한다. 이 세션에서는 코드와 두 원본 설계 문서를 수정하지 않는다.

현재 문서에는 `Long.MAX_VALUE`가 다음과 같이 서로 다른 의미로 사용된다.

- 부피 제약이 없는 문제의 차량 부피 용량
- 더 이상 가능한 시간창이 없다는 실패 상태
- 점수 합산 시 넘지 않아야 하는 자료형 상한

이 세 의미를 하나의 숫자로 표현하지 않는다. 실제 업무에서 허용하는 최댓값은 유한한 도메인 값으로 표현하고, 계산 실패는 별도 상태로 표현한다.

## 확정 값

1. 부피의 외부 기준 단위는 `CBM`이다.
2. 부피 제약을 사용하지 않는 문제에 적용할 기본 차량 부피 용량은 `999 CBM`이다.
3. 내부 부피 값은 전체 문서에서 합의한 고정소수점 변환 정책을 따른다. 따라서 내부 기본 용량은 개념적으로 `toVolumeUnits(999 CBM)`이다. 이 문서에서 소수 자릿수는 별도로 확정하지 않는다.
4. 시간 계산의 최댓값은 각 `Plan` 입력에서 얻은 `plan end time`이다.
5. `999 CBM`과 `plan end time`은 `Long.MAX_VALUE`를 대체하는 유한한 도메인 한계값이다. 둘 다 실패 sentinel이 아니다.
6. 계산 결과가 한계값을 넘으면 한계값으로 잘라 저장하지 않는다. 해당 배치나 경로를 실행 불가능으로 판정하거나 입력 검증 오류로 처리한다.

`master-design.md`와 `domain-design.md`의 다음 표현은 개정 대상이다.

```text
volume = 0
capacityVolume = Long.MAX_VALUE 또는 MAX
```

개정 후 개념은 다음과 같다.

```text
volume = 0
capacityVolume = toVolumeUnits(999 CBM)
capacityVolumeSource = DEFAULT_FOR_UNUSED_DIMENSION
```

시간 계산 역시 다음과 같이 바뀐다.

```text
허용되는 실제 시각의 상한 = planEndTime
계산 불가능 = 별도 INFEASIBLE 상태
```

## Constants 역할

`Constants`는 의미가 다른 숫자를 모아 두는 범용 파일이 아니라, 시스템 전체에서 동일해야 하는 **기본 수치 정책**만 제공한다.

초기 설계에서 둘 수 있는 항목은 다음과 같다.

```text
DEFAULT_VOLUME_CAPACITY_CBM = 999
SECONDS_PER_DAY = 86_400
```

이때 이름에 `UNLIMITED`, `INFINITY`, `MAX_LONG`을 사용하지 않는다. `999 CBM`은 수학적 무한대가 아니라 현재 합의한 유한한 기본값이기 때문이다.

반면 다음 값은 `Constants`에 두지 않는다.

- `planStartTime`, `planEndTime`: 입력마다 달라지는 계획 값
- 차량이 입력으로 제공한 실제 용량
- 고객사별 비용과 페널티
- 탐색 중 도출된 도착·서비스 시작 시각
- 실행 가능/불가능 상태

설계상 값을 세 층으로 구분한다.

| 층 | 예 | 책임 |
|---|---|---|
| 정적 기본 정책 | `DEFAULT_VOLUME_CAPACITY_CBM = 999` | 입력이 해당 차원을 사용하지 않을 때 적용할 기본값 제공 |
| 계획별 한계 | `planEndTime`, 입력 차량 용량 | 변환 단계에서 `PlanLimits`와 차량 도메인 값으로 확정 |
| 계산 상태 | `FEASIBLE`, `INFEASIBLE` | 경로 전파와 삽입 평가의 결과 표현 |

`MAX_PENALTY` 같은 점수 안전 한계가 필요하더라도 용량·시간 상수와 분리한다. 예를 들어 `CapacityDefaults`, `ScoreLimits`, `TimeUnits`처럼 의미별 namespace를 사용한다. 이렇게 해야 `999`를 점수 또는 시간의 특별한 값으로 오해하지 않는다.

`PlanLimits`는 적어도 다음 값을 가진 계획별 불변 객체로 설명한다.

```text
planStartTime
planEndTime
planDurationSec
```

상수 기본값이 바뀌면 결과 재현성에 영향을 줄 수 있다. 실행 결과 메타데이터에는 최소한 솔버 버전과 적용된 기본 부피 용량을 남긴다. 고객사별로 값이 달라지는 요구가 생기면 `Constants`를 조건문으로 늘리지 않고 고객사 설정 또는 `SiteProfile`이 명시적으로 기본 정책을 제공하게 한다.

## 시간 불가능 표현

`TimeWindowSet.earliestStartFrom`과 `arrivalAfterTravel`은 `Long.MAX_VALUE`를 반환하지 않는다. 실행 가능 여부와 실제 시각을 분리한 결과 타입을 사용한다.

개념적인 결과는 다음과 같다.

```text
TimeResult
├─ FEASIBLE(time)
└─ INFEASIBLE(reason)
```

초기 구현에서 객체 할당 비용을 피해야 한다면 다음과 같이 상태와 값이 분리된 동등한 표현을 사용할 수 있다.

```text
status = FEASIBLE | INFEASIBLE
time = status가 FEASIBLE일 때만 읽을 수 있는 long
reason = NO_TIME_WINDOW | OUTSIDE_PLAN | NO_WORK_WINDOW | TIME_OVERFLOW | ...
```

핵심 계약은 다음과 같다.

- `planEndTime`은 가능한 실제 시각의 최댓값이지 `INFEASIBLE` 표시가 아니다.
- `INFEASIBLE` 결과에는 후속 서비스 시간이나 이동시간을 더하지 않는다.
- `planEndTime + 1`도 sentinel로 사용하지 않는다.
- 시간 덧셈과 배율 계산은 checked arithmetic을 사용한다.
- 중간 계산이 자료형 범위를 넘으면 `TIME_OVERFLOW`로 실패한다.
- 중간 계산은 안전하지만 결과가 계획 종료를 넘으면 `OUTSIDE_PLAN`으로 실패한다.
- 실패 원인은 경로 실행 가능 판정과 최종 미배정 진단에 전달할 수 있어야 한다.

`TimeWindowSet` 자체는 계획 기간 안으로 정규화된 창만 보유한다. 마지막 창 이후를 조회하면 `INFEASIBLE(NO_TIME_WINDOW)`를 반환한다. 경로 전파는 실패를 확인한 즉시 중단하며, 실패 상태가 들어 있는 배열 원소에 산술 연산을 수행하지 않는다.

## 무제한의 의미

설계 문서에서 “무제한 부피”라는 표현은 다음과 같이 해석한다.

> 해당 문제에서는 부피 차원을 제약으로 사용하지 않으며, 공통 2차원 용량 계산 구조를 유지하기 위해 주문 부피를 `0`, 차량 기본 부피 용량을 `999 CBM`으로 변환한다.

따라서 `999 CBM` 자체가 무한대인 것은 아니다. 다음 규칙을 적용한다.

- 입력에 실제 차량 부피 용량이 있으면 그 값을 사용한다.
- 부피 차원을 사용하지 않는 변환 정책에서만 `999 CBM` 기본값을 사용한다.
- 기본값을 적용했다는 사실을 `capacityVolumeSource` 등의 provenance로 보존한다.
- 실제 부피 수요가 있는 문제에서 용량이 누락되었을 때 자동으로 “무제한”이라 간주하지 않는다. 이 경우의 정책은 아래 남은 질문으로 기록한다.
- 실제 합계가 `999 CBM`을 넘는 값을 `999 CBM`으로 잘라서 통과시키지 않는다.
- 향후 기본값을 조정해도 도메인 로직에는 `999` 비교 분기를 추가하지 않는다. 변환이 끝난 뒤 엔진은 모든 차량 용량을 일반적인 유한 정수 값으로 동일하게 처리한다.

이 구조는 현재의 2차원 용량 전파를 그대로 유지하면서도 특별한 숫자에 알고리즘 의미가 결합되는 것을 막는다.

## validation

변환 단계에서 다음을 검증한다.

### 부피

- 입력 부피의 단위가 `CBM`인지 확인한다.
- 주문 부피와 차량 부피 용량은 음수가 아니어야 한다.
- 합의된 소수 자릿수 및 변환 규칙을 한 곳에서 적용한다.
- `부피 × 수량`, 경로 누적 부피, 내부 단위 변환은 overflow를 검사한다.
- 명시적 차량 용량과 기본값의 출처를 구분한다.
- 입력 차량 용량이 존재하면 `999 CBM`으로 덮어쓰지 않는다.
- 허용 정밀도를 넘는 값은 합의된 변환 규칙을 적용하되, 변환 전후 값과 정책을 로그 또는 결과 메타데이터로 추적할 수 있어야 한다.
- `Long.MAX_VALUE`, 무한대, `NaN`을 외부 입력이나 내부 용량 값으로 허용하지 않는다.

### 시간

- `planStartTime < planEndTime`이어야 한다.
- 모든 시간창을 계획의 기준 시각과 동일한 시간축으로 변환한다.
- 계획 기간을 상대 초로 변환할 때 자료형 범위를 검사한다.
- 이동시간, 서비스시간, 대기시간은 음수가 아니어야 한다.
- 도착·서비스 시작·서비스 종료 계산에서 매 덧셈을 검사한다.
- 계산값이 `planEndTime`을 넘으면 값을 `planEndTime`으로 보정하지 않고 실행 불가능으로 판정한다.
- 입력 시간창이 계획 범위와 겹치지 않으면 빈 창 또는 명시적 입력 진단으로 변환한다.
- 직렬화 결과에 `Long.MAX_VALUE`를 실제 시각처럼 기록하지 않는다.

### 설정 안전성

- 애플리케이션 시작 시 기본 `999 CBM`이 선택된 내부 scale에서 안전하게 표현되는지 확인한다.
- 점수·거리·시간·용량 한계는 서로 독립적으로 검증한다.
- 설정 변경으로 기존 입력이 달라지는 경우 조용히 결과를 바꾸지 않도록 설정값 또는 정책 버전을 실행 결과에 기록한다.

## 테스트

최소 테스트 범위는 다음과 같다.

### 부피 기본값

1. 부피 차원을 사용하지 않는 문제는 모든 주문 부피가 `0`이고 기본 차량 용량이 정확히 `999 CBM` 내부 값으로 변환된다.
2. 실제 차량 부피 용량이 있으면 기본값 대신 실제 값이 유지된다.
3. `999 CBM` 경계의 부피는 합의된 `<=` 용량 규칙에 따라 허용된다.
4. `999 CBM`을 초과하는 실제 부피를 임의로 `999 CBM`으로 자르지 않는다.
5. 부피와 수량의 곱 및 경로 합계 overflow를 검출한다.
6. scale 변경 또는 소수 자릿수 경계에서 합의한 변환 결과가 유지된다.

### 계획 종료

1. 계획 종료 직전의 가능한 시각을 정상 값으로 반환한다.
2. 계획 종료 경계의 포함 여부를 확정한 뒤 그 계약을 테스트한다.
3. 계획 종료를 1초라도 넘는 도착 또는 서비스 이벤트는 `OUTSIDE_PLAN`이다.
4. 마지막 시간창 이후 조회는 숫자 sentinel이 아닌 `INFEASIBLE(NO_TIME_WINDOW)`다.
5. 근무창이 소진된 이동은 `INFEASIBLE(NO_WORK_WINDOW)`다.
6. 매우 큰 이동시간·서비스시간의 덧셈은 음수로 wrap-around하지 않고 `TIME_OVERFLOW`다.
7. 실패 결과에 후속 시간을 더하려는 사용을 API 계약 또는 assertion으로 차단한다.

### 회귀 및 속성 테스트

- 유효한 경로의 모든 시각은 계획 범위 안에 있다.
- 유효한 경로의 누적 부피는 차량의 유한 용량 이하이다.
- 어떠한 실행 결과 JSON에도 `Long.MAX_VALUE`가 시각이나 용량으로 노출되지 않는다.
- `win_poc_case.json` 회귀 실행에서 한계값 정책 변경 전후의 차이는 의도한 항목으로만 제한된다.

## 남은 질문

다음 사항은 이번 답변만으로 확정할 수 없으므로 마스터 설계 개정 전에 질문으로 남긴다.

1. `plan end time`은 포함 경계인가, 제외 경계인가? 권장 기본은 시간 구간을 `[planStartTime, planEndTime)`로 표현하는 것이다.
2. 계획 종료 제한은 서비스 **시작**에만 적용하는가, 서비스 **완료**와 최종 depot 복귀에도 적용하는가?
3. 실제 업무 입력에서 주문 부피는 존재하지만 차량 부피 용량이 누락된 경우에도 `999 CBM`을 기본 적용할 것인가, 아니면 입력 오류로 처리할 것인가?
4. `999 CBM`은 전체 시스템 공통 기본값인가, 고객사 `SiteProfile`별로 재정의할 수 있는 기본값인가?
5. 명시적으로 `999 CBM`보다 큰 차량 용량이 들어오는 경우 허용할 것인가? 허용한다면 `999 CBM`은 시스템 상한이 아니라 누락/미사용 차원용 기본값으로만 정의해야 한다.
6. 실행 결과에 남길 정책 식별자는 솔버 버전만으로 충분한가, 별도의 `numericPolicyVersion`이 필요한가?

위 질문에 답하기 전까지 구현 계획에는 다음 가정을 사용한다.

```text
999 CBM = 부피 차원 미사용 시의 기본 유한 용량
planEndTime = 계획마다 입력에서 파생되는 시간 상한
INFEASIBLE = 숫자가 아닌 명시적 상태
```
