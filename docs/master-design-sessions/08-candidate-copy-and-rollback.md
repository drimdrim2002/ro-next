# 세션 08 — 후보 해 복사와 롤백 전략

이 문서는 `master-design.md`의 후보 해 생성·수용·롤백 정책을 구체화하기 위한 작업 기록이다. 이 세션의 범위는 `Route`, `Solution`, `RequestBank`, ALNS candidate, `FleetMinimizer`, 캐시 무효화와 Phase 15의 `undo-log`이다. 실제 코드 구조나 API 이름은 구현 시 조정할 수 있지만, 아래 상태 전이와 불변조건은 유지해야 한다.

## 확정 정책

### 1. 단계적 구현 원칙

후보 해 처리 방식은 다음 두 단계로 구현한다.

1. 초기 안전 구현: 변경되는 `Route`만 복사하는 copy-on-write와 `RequestBank` 복사를 사용한다.
2. 성능 최적화: Phase 15에서 프로파일링 결과가 필요성을 입증하면 `Move.apply/undo`와 `UndoLog`로 교체한다.

초기 단계에서도 `Solution` 전체를 반복마다 깊은 복사하지 않는다. 반대로 Phase 15의 `undo-log`가 준비되기 전부터 원본 해를 직접 수정한 뒤 수작업으로 복구하는 방식도 사용하지 않는다.

### 2. 커밋된 해는 불변 스냅샷이다

ALNS가 보관하는 상태를 다음과 같이 구분한다.

- `currentSolution`: 다음 반복의 기준이 되는 커밋된 해
- `bestSolution`: 지금까지 발견한 최선의 커밋된 해
- `candidate`: 현재 반복에서만 변경할 수 있는 임시 작업 상태

`currentSolution`과 `bestSolution`은 생성된 뒤 외부에서 변경할 수 없는 스냅샷으로 취급한다. destroy, repair와 `FleetMinimizer`는 오직 `candidate`를 통해서만 상태를 변경한다. 후보가 수용되기 전에는 커밋된 해의 `Route`, `RequestBank`, 캐시, 구조 해시를 직접 변경할 수 없다.

`ProblemInstance`, `TravelMatrix`, 노드와 요청 배열처럼 문제 자체에 속한 불변 데이터는 모든 해가 공유한다.

### 3. 해의 요청 소유권 불변조건

관찰 가능한 모든 상태에서 각 요청은 정확히 다음 둘 중 한 곳에만 존재해야 한다.

- 정확히 하나의 차량 경로에 픽업·배송 노드가 함께 존재
- `RequestBank`에 미배정 요청으로 존재

픽업과 배송의 제거·삽입은 요청 단위의 원자 연산으로 제공한다. 호출자가 픽업 노드만 제거하거나 배송 노드만 삽입하는 저수준 변경 API를 직접 사용할 수 없게 한다. 원자 연산 내부의 순간적인 중간 상태는 외부 평가·검증·연산자 선택에 노출하지 않는다.

### 4. 롤백의 의미

초기 안전 구현에서 롤백은 역연산을 실행하는 것이 아니라 `candidate`를 폐기하고 기존 `currentSolution`을 계속 사용하는 것이다. 따라서 거절된 후보, 실행 불가능한 후보, 연산자 예외, 취소와 보조 시간 제한은 모두 같은 폐기 경로를 사용한다.

Phase 15 이후의 롤백은 `UndoLog`를 역순으로 적용하여 탐색 전 상태로 되돌리는 것을 뜻한다. 두 단계는 내부 구현은 다르지만, 외부에서 관찰되는 수용·폐기 결과는 같아야 한다.

## 초기 안전 구현

### 1. `Solution`과 `CandidateSolution`의 역할

개념적인 구조는 다음과 같다.

```text
Solution (불변 스냅샷)
├─ Route[]
├─ RequestBank
├─ solution-level summary/cache
└─ structuralHash

CandidateSolution (한 반복의 변경 경계)
├─ base: Solution
├─ working Route[]
├─ copiedRouteIds
├─ copied RequestBank
└─ invalidated solution-level state
```

후보 생성 시 `Route[]` 컨테이너는 얕게 복사할 수 있다. 각 원소는 처음에는 기준 해의 `Route`를 가리킨다. 특정 차량 경로를 처음 변경하려는 시점에만 해당 경로의 구조를 복사하고 `working Route[]`의 참조를 교체한다. 이후 같은 후보 안에서 그 경로를 다시 변경할 때는 이미 복사된 인스턴스를 재사용한다.

이 계약은 다음과 같이 표현할 수 있다.

```text
candidate.editRoute(vehicleId)
  ├─ 아직 복사하지 않음 → Route 구조 복사, 캐시 무효화, copied 표시
  └─ 이미 복사함       → 기존 working Route 반환
```

destroy가 2개 경로를 변경하고 repair가 3개 경로를 추가로 변경했다면 최대 5개 경로만 복사한다. 변경하지 않은 경로는 기준 해와 공유하되, 공유 중인 경로에는 어떤 변경 API도 호출할 수 없다.

### 2. `Route` 복사 범위

첫 변경을 위한 경로 복사는 최소한 다음 구조 상태를 독립적으로 보유해야 한다.

- `vehicleId`
- 유효한 방문 순서 `seq[0..length)`
- `length`
- 경로 활성 여부가 `Route`에 속한다면 해당 상태
- 경로 구조 버전 또는 변경 세대

`ProblemInstance`는 불변이므로 참조를 공유한다. 변경될 경로의 파생 캐시는 복사하지 않고 무효 상태로 시작하는 것을 기본으로 한다. 즉, `arrival`, `serviceStart`, 적재량 배열, `RouteMetrics` 등의 값은 필요할 때 정확한 전방 1-pass로 다시 계산한다.

변경하지 않은 공유 경로의 유효한 캐시는 그대로 재사용할 수 있다. 이 때문에 초기 버전도 전체 해 재계산이 아니라 변경 경로 재계산만 수행할 수 있다.

### 3. `RequestBank` 복사

후보 생성 시 `RequestBank`의 내부 `BitSet`은 독립 복사한다. 이는 해의 전체 경로를 복사하는 것보다 비용이 작고, destroy/repair 과정에서 가장 자주 변경되는 요청 소유권을 안전하게 격리한다.

후보의 `RequestBank` 변경은 다음 요청 단위 연산을 통해서만 이루어진다.

```text
unassign(requestId, routeId)
  = 경로에서 픽업·배송 쌍 제거 + RequestBank 비트 설정

assign(requestId, routeId, pickupPos, deliveryPos)
  = 경로에 픽업·배송 쌍 삽입 + RequestBank 비트 해제
```

두 동작 중 하나만 성공한 상태를 후보 외부에 노출해서는 안 된다. 사전조건 위반이나 삽입 실패 시 해당 원자 연산 자체가 상태를 변경하지 않아야 한다.

### 4. 삽입 후보 평가와 실제 반영의 분리

`InsertionEvaluator`가 가능한 모든 위치를 평가하는 동안 `currentSolution`이나 보관 중인 후보 경로를 시험적으로 변경해서는 안 된다. 초기 구현은 다음 중 하나의 안전한 평가 방식을 사용한다.

- 평가 전용 scratch 경로에 대상 경로 구조를 복사해 전체 1-pass 계산
- 경로와 삽입 위치를 입력으로 받아 임시 순서를 계산하는 순수 평가 함수

여러 삽입 위치 중 최종 선택된 `InsertionMove`만 `CandidateSolution.assign(...)`을 통해 실제 후보에 반영한다. 초기에는 속도보다 평가 결과와 반영 결과가 정확히 일치하는 것이 우선이다.

### 5. 최선 해 보존

copy-on-write 단계에서 `bestSolution`은 불변 `Route`를 `currentSolution`과 공유할 수 있다. 이후의 모든 변경이 반드시 새 후보의 경로 복사 뒤에 이루어지기 때문이다. 다만 `Route[]` 컨테이너, `RequestBank`, 해 수준 요약과 구조 해시는 각 스냅샷의 독립된 값이어야 한다.

공유 객체의 불변성을 API로 강제하기 어렵다면, 초기 구현에서는 새로운 전역 최선 해가 나올 때만 독립 스냅샷을 만드는 쪽을 선택한다. 매 반복 전체 복사보다 빈도가 낮고, 최선 해 오염 위험을 제거할 수 있다.

## 승인·폐기 흐름

### 1. 일반 ALNS 반복

한 번의 반복은 다음 순서를 따른다.

```text
base = currentSolution
→ CandidateSolution 생성
→ destroy: 요청 쌍 제거 및 RequestBank 등록
→ repair: 요청 쌍 삽입 및 RequestBank 해제
→ 후보 불변조건·경로 실행 가능성 검증
→ 후보 점수 계산
→ Simulated Annealing 수용 판정
   ├─ 수용: candidate.freeze()를 새 currentSolution으로 교체
   └─ 거절: candidate 폐기, 기존 currentSolution 유지
→ 전역 최선이면 bestSolution 갱신
→ 결과 분류에 따라 연산자 보상 기록
```

`freeze()` 이후에는 후보의 변경 API를 호출할 수 없다. 수용된 후보가 `currentSolution`이 된 뒤 다음 반복에서는 다시 새로운 후보 변경 경계를 연다.

후보 생성부터 수용 판정까지 예외가 발생하거나 보조 시간 제한·취소가 확인되면 후보를 폐기한다. 이때 기준 해는 처음부터 변경되지 않았으므로 별도 복구가 필요하지 않다.

### 2. `FleetMinimizer`

`FleetMinimizer`도 별도 롤백 방식을 만들지 않고 동일한 후보 계약을 사용한다.

```text
base = 차량 수 최소화 단계의 currentSolution
→ CandidateSolution 생성
→ 제거 대상 차량 경로의 모든 요청을 원자적으로 RequestBank로 이동
→ 다른 차량 경로로 전부 재삽입 시도
   ├─ 전부 성공 + 후보 유효: freeze 후 승인
   └─ 하나라도 실패: 후보 전체 폐기
```

실패 시 요청을 원래 위치에 하나씩 다시 삽입하는 보상 로직을 작성하지 않는다. 선택된 원본 차량 경로와 재삽입으로 변경된 대상 경로만 복사되므로, 실패한 시도의 비용도 전체 해 깊은 복사보다 제한적이다.

차량 제거 성공 여부는 단순히 경로가 비었는지만 보지 않고 `Solution`이 사용하는 차량 활성 상태와 목적함수 정의에 따라 판정해야 한다.

### 3. 구조 검증 시점

다음 경계에서는 최소한 요청 소유권과 경로 구조를 검증한다.

- 초기해 생성 완료
- destroy/repair가 끝난 후보의 평가 직전
- 후보 승인 직전
- `FleetMinimizer` 성공 승인 직전
- 최종 결과 복원 직전

개발·테스트 모드에서는 각 요청 단위 변경 직후에도 검증할 수 있다. 운영 hot loop에서는 비용을 측정한 뒤 검증 수준을 조정하되, 승인 경계 검증은 유지한다.

`structuralHash`는 빠른 변화 감지와 중복 후보 탐지에 사용할 수 있지만, 해의 정확성을 증명하지는 않는다. 해시 충돌 가능성이 있으므로 핵심 불변조건 검증을 구조 해시 비교로 대체하지 않는다.

## 캐시 규칙

### 1. 캐시는 파생 상태다

방문 순서, 요청 소유권과 차량 활성 상태가 원본 상태이며, 다음 값은 언제든 원본에서 재계산할 수 있는 파생 상태다.

- `arrival`, `serviceStart`
- 무게·부피 적재량
- 거리, 운전시간, 대기시간, 서비스시간
- `RouteFeasibility`, `RouteMetrics`
- 해 전체 점수와 목적 벡터
- `structuralHash`
- `InsertionCostTable`

캐시 복구가 구조 복구보다 우선해서는 안 된다. 캐시가 의심스러우면 폐기하고 전체 전방 계산으로 다시 만든다.

### 2. 경로 캐시 무효화

다음 변경은 해당 경로의 캐시를 즉시 무효화한다.

- 요청 삽입·제거
- 노드 순서 변경
- 경로의 차량 또는 terminal 변경
- 차량 활성 상태 변경이 경로 평가에 영향을 주는 경우
- `copyFrom`과 같은 구조 덮어쓰기

초기 copy-on-write 경로는 첫 구조 변경 전에 캐시 무효 상태로 만든다. 경로의 `metrics()` 또는 점수 계산이 처음 필요할 때 정확한 1-pass로 채운다. 변경하지 않은 공유 경로의 캐시는 해당 경로와 차량이 동일하다는 전제에서만 재사용한다.

### 3. 해 수준 캐시 무효화

경로 하나라도 바뀌거나 `RequestBank`의 비트가 바뀌면 다음 해 수준 값은 무효화한다.

- 전체 비용 또는 고객사별 목적 벡터
- 미배정 수와 미배정 패널티 합
- 사용 차량 수
- 전체 거리·시간 집계
- 구조 해시

`RequestBank` 변경은 개별 경로의 시간·거리 캐시를 무효화하지 않지만 해 전체 점수와 삽입 가능 후보 집합에는 영향을 준다.

### 4. `InsertionCostTable` 키와 수명

삽입 비용 캐시는 최소한 다음 상태를 구분해야 한다.

```text
routeId 또는 vehicleId
routeVersion
requestId
pickupPosition
deliveryPosition
평가 정책/설정 버전
```

경로 구조가 바뀌면 `routeVersion`을 증가시키고 이전 버전의 삽입 비용을 재사용하지 않는다. 요청 소유권이나 고객사 정책이 삽입 비용에 영향을 주는 경우에는 solution/request-bank 세대와 정책 버전도 키에 포함하거나, 관련 테이블을 일괄 폐기한다.

차량별 속도·근무창 때문에 같은 노드 순서라도 차량이 다르면 캐시를 공유할 수 없다. 캐시 키에 차량 정체성이 반드시 반영되어야 한다.

### 5. 캐시 일관성 기준

모든 승인된 해에 대해 다음 등식이 성립해야 한다.

```text
캐시를 사용한 RouteMetrics/목적값
=
캐시를 비우고 전체 전방 재계산한 RouteMetrics/목적값
```

Phase 15 최적화 전후에도 이 기준은 바뀌지 않는다.

## 성능 단계 전환

### 1. 전환 조건

`undo-log`는 Phase 15에 자동으로 도입하는 기능이 아니라, JMH와 실제 benchmark fixture의 프로파일링에서 경로 복사와 scratch 평가가 의미 있는 병목으로 확인될 때 도입한다. 전환 전에 다음 지표를 기록한다.

- 반복당 복사된 경로 수와 노드 수
- 삽입 평가용 scratch 복사 횟수
- 경로 복사·배열 할당에 사용된 시간과 allocation rate
- GC 시간
- 전체 solve time에서 후보 복사가 차지하는 비율

copy-on-write가 병목이 아니라면 더 복잡한 `apply/undo`를 도입하지 않거나 도입 범위를 제한할 수 있다.

### 2. Phase 15 이전에 확정할 API 경계

실제 `UndoLog` 구현은 Phase 15에 두더라도 다음 변경 경계는 Phase 2와 Phase 5부터 지켜야 한다.

- 경로 변경은 `Move` 또는 요청 단위 mutation API를 통해서만 수행
- 픽업·배송 쌍과 `RequestBank` 비트의 동시 변경
- 평가와 실제 반영의 분리
- 승인·폐기 결과가 연산자 구현과 분리
- 캐시 무효화가 모든 mutation API 내부에서 일관되게 수행

이 경계를 지켜야 Phase 15에서 알고리즘과 연산자를 다시 작성하지 않고 저장 전략만 바꿀 수 있다.

### 3. `apply/undo` 계약

성능 단계에서는 현재 해를 한 반복 동안 제한적으로 변경하고, 모든 원본 상태를 `UndoLog`에 기록한다.

```text
begin transaction
→ Move.apply(mutableCurrent, undoLog)
→ 후보 평가
   ├─ 수용: commit, undoLog 폐기
   └─ 거절: undoLog를 역순 적용
→ transaction 종료
```

`UndoLog`는 적어도 다음 구조 상태를 정확히 복원할 수 있어야 한다.

- 경로별 변경 전 노드 순서와 길이 또는 동등한 구간 편집 정보
- 변경 전 `RequestBank` 비트
- 차량 활성 상태
- 해 수준 집계에 원본 상태가 있다면 해당 값

여러 `Move`가 한 후보를 구성하면 undo entry를 적용의 반대 순서로 실행한다. 중간 `Move` 실패, 예외, 취소와 시간 제한도 동일한 transaction 종료 경로를 통해 전부 undo한다. 부분 적용된 후보가 다음 반복으로 넘어갈 수 없다.

### 4. `undo`와 캐시 버전

가장 안전한 첫 `UndoLog` 구현에서는 구조만 정확히 복구하고 변경된 경로와 해 수준 캐시는 무효 상태로 둔다. undo 과정에서 과거 캐시 배열까지 되살리려 하지 않고, 다음 접근 때 전체 1-pass로 재계산한다.

`routeVersion`은 apply와 undo 모두에서 단조 증가시키며 이전 값으로 되돌리지 않는 것을 권장한다. 그러면 되돌린 구조가 우연히 과거와 같더라도 변경 도중 만들어진 `InsertionCostTable` 항목을 잘못 재사용하지 않는다.

### 5. 최선 해 격리

`apply/undo` 단계에서는 `currentSolution`의 경로가 transaction 중 직접 변경될 수 있으므로 `bestSolution`이 같은 가변 경로를 공유해서는 안 된다. 새로운 전역 최선 해가 발견될 때 `bestSolution`을 독립 스냅샷으로 보존한다. 최선 해 갱신은 매 반복 발생하지 않으므로 이 복사는 반복별 전체 깊은 복사를 피한다는 원칙과 양립한다.

### 6. 전환 완료 기준

copy-on-write 엔진과 `apply/undo` 엔진은 동일한 입력, 설정, 연산자 선택 순서와 난수 시드에서 다음이 같아야 한다.

- 각 반복의 수용·거절 판정
- 승인된 해의 구조와 요청 소유권
- 목적값
- 최종 해와 최선 해

부동소수점 비교가 개입한다면 기존 결정성 정책에 맞는 동일한 정수 또는 명시적 비교 규칙을 사용한다. 결과 동등성과 캐시 일관성이 입증된 뒤에만 `apply/undo`를 기본 경로로 전환한다.

## 테스트

### 1. copy-on-write 격리

- 후보에서 한 경로를 변경해도 기준 해의 같은 경로 순서와 캐시가 바뀌지 않는다.
- 변경하지 않은 경로는 안전하게 공유된다.
- 같은 후보에서 동일 경로를 여러 번 변경해도 첫 변경 시에만 구조 복사가 발생한다.
- 후보의 `RequestBank` 변경이 기준 해의 비트에 영향을 주지 않는다.

### 2. 승인·폐기

- 수용된 후보만 새 `currentSolution`이 된다.
- 거절된 후보를 폐기한 뒤 기준 해의 구조·요청 소유권·점수가 완전히 동일하다.
- destroy 중 예외, repair 중 예외, 평가 중 예외, 취소와 시간 제한 시 후보가 폐기된다.
- `bestSolution`은 이후 후보 탐색에도 변경되지 않는다.

### 3. 요청 원자성

- 요청 제거 후 픽업과 배송이 모두 경로에서 사라지고 `RequestBank` 비트가 설정된다.
- 요청 삽입 후 픽업과 배송이 같은 차량에 올바른 순서로 존재하고 비트가 해제된다.
- 실패한 삽입은 경로와 `RequestBank`를 모두 변경하지 않는다.
- 무작위 destroy/repair 연속 실행 뒤에도 모든 요청이 경로 또는 `RequestBank` 중 정확히 한 곳에 있다.

### 4. `FleetMinimizer` 롤백

- 모든 요청의 재삽입 성공 시에만 차량 제거 후보가 승인된다.
- 마지막 요청에서 재삽입이 실패해도 기준 해가 정확히 보존된다.
- 재삽입 대상이 여러 경로인 경우에도 실패 시 부분 변경이 남지 않는다.
- 빈 경로와 차량 활성 상태, 사용 차량 수 집계가 일관된다.

### 5. 캐시

- 변경 경로만 캐시가 무효화되고 변경하지 않은 경로 캐시는 유지된다.
- `RequestBank`만 변경되면 해 수준 목적값은 무효화된다.
- 차량이 다른 경로끼리 시간 캐시를 공유하지 않는다.
- route version 변경 후 이전 `InsertionCostTable` 항목이 사용되지 않는다.
- 후보 승인 및 폐기 뒤 캐시 결과가 전체 재계산 결과와 일치한다.

### 6. `UndoLog` 동등성

- 각 `Move`에 대해 `state → apply → undo` 후 구조 fingerprint가 원래와 같다.
- 여러 `Move`를 적용한 뒤 역순 undo하면 원래 해로 돌아간다.
- 중간 예외에도 이미 적용된 모든 entry가 undo된다.
- undo 뒤 캐시를 비우고 재계산한 결과가 적용 전 결과와 같다.
- 동일 시드로 copy-on-write 경로와 apply/undo 경로의 반복 trace 및 최종 결과를 비교한다.

구조 fingerprint에는 해시 하나만 사용하지 않고 경로별 유효 노드 순서, `RequestBank` 비트, 차량 활성 상태를 포함한다.

## 남은 질문

1. 차량 제거 상태는 빈 `Route`만으로 표현할 것인가, `Solution`에 별도의 `activeVehicle` 비트 집합을 둘 것인가? 이 결정은 `FleetMinimizer`, 사용 차량 수 집계와 `UndoLog` 항목에 영향을 준다.
2. `bestSolution` 보존은 초기 copy-on-write의 불변성 강제를 신뢰해 구조를 공유할 것인가, 단순성을 위해 전역 최선 갱신 시 항상 독립 스냅샷을 만들 것인가? 안전성 기준으로는 후자를 우선 권장한다.
3. 고객사별 `ScorePolicy`가 경로별 측정값의 합만 사용하는가, 아니면 `RequestBank`, 차량 간 균형, 권역별 집계 같은 해 전체 상태를 참조할 수 있는가? 후자라면 solution-level cache key와 무효화 범위를 정책 계약에 포함해야 한다.
4. `InsertionCostTable`을 한 ALNS 반복 안에서만 사용할 것인가, 여러 반복에 걸쳐 유지할 것인가? 초기 안전 구현은 반복 단위 폐기를 권장하며, 장기 캐시는 Phase 15 측정 후 결정한다.
5. 운영 모드에서 승인 직전 전체 구조 검증을 항상 수행할 것인가, 문제 크기가 큰 경우 샘플링 또는 설정 옵션으로 낮출 것인가? 정확성 기준 검증과 진단 모드는 반드시 유지해야 한다.
6. Phase 15에서 `apply/undo`가 이득이 없으면 Phase 산출물을 “프로파일링과 전환 판단 기록”으로 완료 처리할 수 있는가? 이 문서는 실제 병목이 아닐 경우 copy-on-write 유지를 권장한다.
